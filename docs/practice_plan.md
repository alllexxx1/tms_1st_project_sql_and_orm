# План практики для преподавателя

## Цель

За 180 минут пройти путь от SQL-запросов в Python до аналогичного приложения
на SQLAlchemy. Студенты должны увидеть, какие запросы выполняет приложение,
что меняется при использовании ORM и зачем нужны миграции.

Подготовку PostgreSQL и установку зависимостей желательно выполнить
до занятия. Если подготовка затянется, часть однотипных CRUD-операций
можно завершить самостоятельно по уже разобранному примеру.

## Модель данных

Используем три таблицы:

| Таблица | Основные поля | Назначение |
| --- | --- | --- |
| `events` | `id`, `title`, `venue`, `starts_at` | Мероприятия с площадкой и датой начала |
| `seats` | `id`, `event_id`, `row_number`, `seat_number` | Пронумерованные места на конкретное мероприятие |
| `tickets` | `id`, `seat_id`, `customer_name` | Действующие бронирования |

Связи: мероприятие содержит много мест, место может иметь не более одного
действующего билета. Мероприятие билета определяется через его место,
поэтому отдельный `event_id` в билете не нужен.

`venue` является названием площадки, например «Малый зал».
Не создаем отдельный справочник залов: набор мест задается для каждого
мероприятия. Это учебное упрощение, которое позволяет ограничиться тремя
таблицами и не проверять соответствие зала мероприятия залу места.

## Правила

1. Названия мероприятий и площадок, имя покупателя не могут быть пустыми.
2. Номера ряда и места являются положительными целыми числами.
3. В пределах мероприятия сочетание ряда и номера места уникально:
   `UNIQUE (event_id, row_number, seat_number)`.
4. У одного места может быть только один действующий билет:
   `UNIQUE (seat_id)`. Ограничение БД защищает и от одновременного бронирования.
5. Билет можно создать только для существующего места.
6. Отмена удаляет билет; после этого место можно забронировать снова.
7. Забронированное место нельзя удалить или перенести на другое мероприятие.
   У мероприятия с билетами нельзя менять площадку или удалять его.
   Связанные записи защищаем внешними ключами, дополнительные правила
   проверяем в коде приложения.
8. Мероприятие без билетов можно удалить вместе с его местами.
9. Название места для пользователя имеет вид «ряд 2, место 5».
   Поиск места выполняется в контексте выбранного мероприятия.

На этапе схемы удаление защищают внешние ключи: `seats.event_id` использует
`ON DELETE CASCADE`, а `tickets.seat_id` использует `ON DELETE RESTRICT`.
Если у мероприятия есть билет, каскадное удаление его мест будет отклонено,
и мероприятие останется в базе. Проверки изменения площадки и переноса
забронированного места добавим на этапе CRUD.

При бронировании выполняем `INSERT` и обрабатываем нарушение уникальности.
Предварительная проверка свободного места сама по себе не защищает
от одновременных запросов. После ошибки транзакция должна откатиться,
а приложение должно продолжить работу.

## Распределение времени

| Время | Работа |
| --- | --- |
| 0–10 минут | Задача, подключение, схема и связи |
| 10–30 минут | SQL-схема, ограничения и демонстрационные данные |
| 30–55 минут | CRUD мероприятий и мест, параметры запросов |
| 55–85 минут | Свободные места, JOIN, бронирование, отмена, простое меню |
| 85–95 минут | Перерыв |
| 95–120 минут | Модели SQLAlchemy, `Session`, первая миграция Alembic |
| 120–155 минут | Повторяем операции через ORM, используем готовое меню |
| 155–170 минут | Меняем модель и создаем вторую миграцию |
| 170–180 минут | Проверяем сценарии и сравниваем SQL с ORM |

На занятии подробно разбираем один пример каждой операции. Однотипные
функции студенты дописывают по образцу. Консольный ввод остается простым,
чтобы основная часть времени ушла на работу с БД.

## Этапы реализации и коммиты

1. **Подготовка проекта.** Зависимости, настройки в `.env`, проверка подключения,
   README и этот план.
2. **Схема raw SQL.** Таблицы, ограничения, небольшие демонстрационные данные
   и отдельные функции создания таблиц и заполнения примерами.
3. **CRUD и поиск на raw SQL.** Функции мероприятий и мест, поиск, начало меню.
4. **Бронирование на raw SQL.** Список свободных мест, создание и отмена билета,
   завершение первой версии меню, обработка ошибок БД и проверка сценариев.
5. **Модели ORM и Alembic.** Аналогичная схема в отдельной базе,
   первая миграция и демонстрационные данные.
6. **Операции ORM.** Те же функции на SQLAlchemy, подключение к готовому меню,
   проверка одинакового поведения двух реализаций.
7. **Изменение схемы и завершение.** Небольшое поле описания мероприятия,
   вторая миграция, актуальные инструкции и итоговая проверка.

Каждый этап завершаем отдельно. После реализации и проверки преподаватель
просматривает изменения и делает коммит. К следующему этапу переходим
после его сообщения.

Готовы этапы 1 и 2. Для второго этапа в консоли Python отдельно вызываем
`create_tables(database_url)` и `seed_data(database_url)`, затем просматриваем
таблицы и результат JOIN из README через SQL-клиент. Каждая функция выполняется
в собственной транзакции. Для ID используем `SERIAL PRIMARY KEY`.

## Сценарии итоговой проверки

- Создать мероприятие и несколько мест, изменить данные, найти мероприятие
  по части названия и по площадке, найти место по ряду и номеру.
- Найти мероприятия, у которых есть место с указанными рядом и номером.
- Забронировать выбранное место и убедиться, что оно исчезло из свободных.
- Повторить бронирование, получить понятное сообщение и продолжить работу.
- Отменить билет и снова забронировать это же место.
- Забронировать такой же ряд и номер на другом мероприятии.
- Попытаться удалить забронированное место или мероприятие с билетами.
- Попытаться добавить повторяющееся место, нулевой номер или пустое название.
- Проверить отказ при несуществующих ID и корректный откат после ошибки.
- Воспроизвести сценарии на обеих версиях в отдельных базах.
- Применить миграции к пустой ORM-базе, откатить и повторно применить
  вторую миграцию на демонстрационных данных.

Базовый набор данных: два мероприятия, по два ряда и три места в каждом
(всего 12 мест), один действующий билет. Этого достаточно, чтобы увидеть
занятые и свободные места, поиск и связи таблиц.
